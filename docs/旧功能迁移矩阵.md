## 2.4 迁移的形态与顺序（设计文档 11:56-62「旧版迁移程序」五步）

1. 为旧版样本建立可追踪清单：JSON/IndexedDB、sidecar、世界包、图片、快照、知识库、同步文件及未知字段。
2. **只读解析副本**，建立旧 ID/字段映射，拒绝读取失败当空；**保存原始文件和摘要**。
3. **在独立新库导入**，报告正文校验、实体数量、引用、附件与暂不支持功能的保留位置。
4. 用户查看差异并**主动切换**，新旧程序**不共用可写目录**。切换前备份，迁移期间**旧库不被重写**。
5. 在新版完成读取、编辑、导出和双端往返，再逐步接管完整业务。回退恢复旧版备份或兼容导出，**不让旧程序打开新库**。

> 🔴 与原版关键差异（必须写进发布说明）：原版 `upstream/docs/3.0-数据迁移指导.md:15` 是
> 「把旧版**整库覆盖**到新版，同一台机器不要反复导入」，且 `:16` 声明「3.0 只在这一版提供一次性导入，
> 更晚的版本将不再识别旧数据」。新版**反向**：只读导入 + 报告 + 用户主动切换 + 旧库永不重写。

## 4.3 结论摘要

1. **原版规模**：496 文件 / 133,925 物理行（122,414 非纯空行），其中**酒馆域独占 27,354 行（20.4%）**、`data/` 种子 15,069 行（11.3%）、AI 相关（`lib/ai` + `lib/aiCore` + `lib/aiTasks`）14,388 行（10.7%）。
2. **功能域 26 个**，其中本轮（P0→P1→P3）内必须完成 **P1 15 域 + P2 6 域 + P3 4 域**；**P5/独立增量 6 域**按设计文档 12:41 明确留给后续，但**数据必须先能只读导入并原样存住**。
3. **P1 的三个真正难点**不是代码量，而是：①52 个页签的 schema 体系（含 getter 与制度四页签工厂，静态解析会漏）；②`order` 整数序 → `order_key` 分数序的重编；③`revisions` 的 seq 分配纪律（禁止 `COUNT(*)`）。
4. **数据迁移 22 条映射（M-01..M-22）**，其中 **4 条带 🔴 硬约束**：M-09（seq 禁用 COUNT）、M-15（worlds 必须落 workspace 级）、M-16（KB `bodies` 是用户原文不可重建，与 `-vec` 派生索引必须分开处理）、M-22（墓碑不可丢，密码必须转 secretRef）。
5. **「拒绝把读取失败当空」12 个处理点（R-01..R-12）已逐条定位到原版代码行**，其中 R-01（`decideDataFileLoad` 的六分支）、R-04（404 与读取失败必须不同类型）、R-06（本机状态未知即中止合并）、R-12（`too-new` 拒绝写入）是**数据可靠性门禁**，必须做成新版回归用例；原版 `syncGuards.test.ts:78,101,245` 三条断言可直搬。
6. **不迁移 18 项**，其中 7 项（N-01..N-07）是原版**也不存在**的能力（全仓 grep 0 命中，已附证据），因此 P3 后端与 P5 插件生态属**从零建设**，排期时不能按「迁移」估工。
