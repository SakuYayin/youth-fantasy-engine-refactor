```ts
       .character() / .outlineNode() / .worldSetting() / .material()
       .attachment() / .asset() / .snapshot() / .job() / .user() / .device()
       .plugin() / .request()
```

**revision / cursor**（🔴 不透明，只能相等比较，禁止排序/算术/数值化）：

```ts
encodeRevision(seq: number): Revision            // seq 必须 >= 1 的安全整数
encodeCursor(seq: number, scope: string): Cursor // seq 必须 >= 0
```

### 🔴 revision 序号从哪来（Lead 裁决，全包统一）

`Revision` 是不透明字符串，**任何地方都不得解析它、更不得拿它做算术或排序**。
但写入端必须知道「下一个 revision 是什么」。解决办法：**把序号以整数列的形式与实体同行存储**。

- 每条带 `revision` 列的表都加 `revision_seq INTEGER NOT NULL DEFAULT 0 CHECK (revision_seq >= 0)`。
- `revisions` 表加 `seq INTEGER NOT NULL`，并有 `UNIQUE (entity_type, entity_id, seq)`。
- 写入时在**同一个 UPDATE**里推进计数器，并用乐观锁保护：

```sql
UPDATE documents
   SET body = ?, revision = ?, revision_seq = revision_seq + 1, updated_at = ?
 WHERE id = ? AND revision = ?
```

- 新 revision 字符串 = `revisionGenerator.next(当前 revision_seq + 1)`（默认实现 `encodeRevision`）。
- **算术只发生在 `number` 上**；`Revision` 字符串永远只做相等比较。

⛔ **禁止**用 `SELECT COUNT(*) FROM revisions` 推序号：版本行一旦被保留期/GC 裁剪，
序号会**倒退**，导致 revision 字符串被**重复使用**，而 outbox 幂等键、`baseRevision`
校验和版本历史全都建立在「同一 revision 字符串永远指向同一版本」之上。这是静默数据损坏。

**时钟**（注入式，禁止直接 `new Date()` 出现在领域层）：

```ts
interface Clock { now(): UtcTimestamp }
systemClock: Clock
fixedClock(iso: string): Clock   // 仅测试用
isUtcTimestamp(value: unknown): value is UtcTimestamp
```

**冲突判定**（🔴 唯一合法的胜负判断入口，禁止自己写"谁更新"）：

```ts
resolveConflict(input: ConflictWinnerInput): ConflictOutcome
// ConflictOutcome =
//   { kind: 'fast-forward' } | { kind: 'already-current' }
//   | { kind: 'conflict'; reason: 'diverged' }
//   | { kind: 'delete-update'; reason: 'local-deleted' | 'remote-deleted' }
```

**错误载体**：

```ts
interface ErrorPayload {
  code: ErrorCode
  message: string          // 面向用户的中文短句
  requestId: RequestId
  severity: ErrorSeverity
  retryable: boolean
  detail?: Readonly<Record<string, string | number | boolean | null>>
  cause?: string           // 仅本地调试，绝不经 IPC/HTTP 外发
}

class ContractError extends Error {
  constructor(payload: {
    code: ErrorCode; message: string; requestId: RequestId
    severity?: ErrorSeverity; retryable?: boolean
    detail?: ...; cause?: string
  })
  toPayload(): ErrorPayload
}
```

## 6. `sync.ts` —— 同步协议 v1

```ts

// limits: { maxOperationsPerBatch: 100, maxBatchBytes: 4MiB, maxOrderKeyLength }
// assets: { enabled, partSizeBytes, maxAssetBytes }

  | { ok: true;  batchId; cursor; acceptedAt; revisions; replayed? }
  | { ok: false; code; requestId; conflicts: readonly OperationConflict[] }

                    currentRevision, reason }

ChangeEntry   { cursor, entityType, entityId, projectId, action, revision,
                baseRevision, payload, committedAt, serverSeq }
ChangesOutput { changes, nextCursor, resyncRequired }
```

🔴 **游标过期的两条路径必须收敛到同一个处理入口**（`packages/contracts/src/sync/index.ts` 的 `ChangesInput` 注释是权威）：

| 路径 | 表达 | 何时 |
| --- | --- | --- |
| A | HTTP 410 + `SYNC_CURSOR_INVALID`（`Result` 的 Err 分支，**不返回 `ChangesOutput`**） | 服务端在处理前就判定游标落在保留窗口外 |
| B | HTTP 200 + `resyncRequired: true` | 组装过程中才发现缺口 |

只实现其中一条的客户端会在另一条上**静默丢弃未同步改动**（不报错、只是丢数据）。
两条路径的处理顺序都是：先保存离线分支 → 再下载快照重放或形成冲突 → 绝不清空未同步稿件。
`resyncRequired === true` 时 `changes` 必须为空——缺口已无法用游标描述，部分应用会卡在「一半新一半旧」。

## 9. 类型安全清单（编译期硬约束）

本项目开了 `strict` + `noUncheckedIndexedAccess` + `noImplicitOverride` +
`verbatimModuleSyntax` + `isolatedModules`。后果：

| 写法 | 结果 |
| --- | --- |
| `arr[0]` | 类型是 `T \| undefined`，必须先判空 |
| `import { SomeType } from '@yfe/contracts'` | ❌ 报错，必须 `import type` |
| `class A { override foo() {} }` 漏 `override` | ❌ 报错 |
| `record[key]` 取值 | 类型含 `undefined` |
| 源码内相对导入 | 必须带 `.js` 后缀（`'./foo.js'`） |
| `any` 穿过 IPC/HTTP 边界 | ❌ 禁止（用 `unknown` + 收窄） |
