# 开发计划

## 交付路线

先发布可独立使用的新桌面写作链路，再加入可靠任务与统一同步后端，随后交付 uni-app x 手机和更多协议，最后完成三平台稳定发布。插件契约、移动接口和安全边界在 P0 定义，不推迟到功能硬编码完成后补。

旧版继续可用，新版单独入口与数据位置。第一条验收链路是离线建作品、创建章节、中文输入、事务保存、崩溃恢复、基础导出、一个可启停主题与字数插件。禁止用“目录和接口已建好”代替可用版本。

## 里程碑与验收

| 阶段 | 实施范围 | 交付物 | 结束条件 |
| --- | --- | --- | --- |
| P0 契约与基准 | 旧功能盘点、版本矩阵、Schema、IPC/API、插件内核与原生依赖原型 | 能运行的三平台最小程序、Android release 原型、协议样本、基准和 ADR | Electron/SQLite ABI、Cordis 生命周期、手机模式、旧数据样本与支持矩阵有证据 |
| P1 单机桌面 | Vue 工作区、Repository、草稿/事务、恢复/导出、内置插件和主题 | 可离线写作的开发预览版、导入报告 | 保存与崩溃验证通过，主线程不承担耗时工作，未支持数据保留 |
| P2 任务与 AI | 持久队列、Worker、统一助手、上下文/检索、建议稿与预算 | 可并行任务的桌面预览版与评测报告 | 多作品不串数据，任务恢复可解释，采用有版本保护，交互基准通过 |
| P3 后端与同步 | 身份/设备/权限、配置与附件、批次/游标/冲突、官方镜像和飞牛部署 | 可配对后端、Web 管理端、桌面双实例往返 | 断网/重复/冲突/删除/撤销通过，HTTPS 与升级恢复通过 |
| P4 uni-app x | 缓存/草稿、基础编辑、配置/任务、配对/同步、远程控制 | 小米真机可用签名 APK、契约一致性报告 | 手机桌面往返不丢数据，锁屏与进程回收可恢复，控制命令鉴权正确 |
| P5 协议与生态 | SMB/FTP/FTPS/SFTP/NFS、模板与工作流包、SDK、核心业务插件迁移 | 驱动能力报告、插件开发示例与导入导出 | 发布驱动通过声明能力，未达标通道明确降级，插件启停与升级通过 |
| P6 稳定发布 | 完整安装矩阵、签名/更新、旧数据迁移、体积与性能收敛、使用文档 | 三平台安装包、Android APK、镜像、恢复指南、发布记录 | 所有发布门禁通过，已知限制可解释，无阻断数据可靠性问题 |

P1 即可给测试用户试写副本；P3 可测 NAS 同步；P4 才形成桌面、手机和后端完整测试闭环。稳定发布在 P6，不把早期预览版宣传成所有协议和全部旧功能完成。

## 依赖与工作安排

核心路径为 P0 → P1 → P3 → P4 → P6。P2 依赖 P1 的事务/任务契约，P5 驱动依赖 P3 的同步规则，插件接口在 P0/P1 先落地。若有多名开发者，可在契约稳定后分别推进桌面/核心、后端/同步、移动；契约变更统一评审，不能各自定义字段和错误码。

首轮开发包按顺序：

1. P0-A：固定源码基线、旧数据副本、构建与功能盘点，记录旧版实际性能。
2. P0-B：数据/版本/任务/插件/IPC/API 契约与样本，Cordis 固定来源和适配器验证。
3. P0-C：Electron utilityProcess、数据库 worker、Vue/CodeMirror 的最小链路，三平台原生模块与 Android 工具链验证。
4. P1-A：本机 SQLite 与 SaveDraft 事务，草稿序号、恢复、导出、ProjectContext。
5. P1-B：简洁工作区、主题与字数插件、只读旧格式导入报告。

每个包保持可构建、可审查，涉及旧数据时使用副本。P0 结束后才大规模搬迁旧模块。

## 旧功能迁移矩阵

P0 从实际入口和数据表建立逐项清单，至少包括作品/卷章、动态设定、人物与关系、世界包、资料/知识库、快照与回收站、模型与提示词、酒馆/角色推演、导入导出及已有同步。每项记录旧入口、数据位置、目标插件、依赖、优先级和验收样本。

基础写作、数据恢复与旧格式读取优先进入 P1；AI 与知识索引进入 P2；统一同步进入 P3。复杂世界观、酒馆、图形关系等按迁移矩阵安排 P5 或独立增量版本。若旧版常用关键功能尚不可用，新版保留其数据和旧版入口，并在发布范围中列明，不自行宣布功能等价。

## 工作量与排期假设

下列是范围预算，不是交付日期。假设一名熟悉 TypeScript/Electron 的开发者全职、可获得 Mac/Linux 验证环境，Android/NAS 测试条件齐备；人周包括实现和相关测试，不等于可简单除以人数的日历工期。

| 阶段 | 初始预算 |
| --- | --- |
| P0 | 2–3 人周 |
| P1 | 4–6 人周 |
| P2 | 3–5 人周 |
| P3 | 4–6 人周 |
| P4 | 3–5 人周 |
| P5 | 4–6 人周 |
| P6 | 2–4 人周 |

基本范围合计 22–35 人周。完整旧版复杂功能迁移需由盘点追加预算，初始预留 8–16 人周；两部分合计 30–51 人周，再预留约 20% 风险储备。不是此前局部 Android/NAS 升级的 10–14 周工程。若多人投入，可缩短部分日历工期，但数据/协议/迁移仍存在顺序依赖。

P0 提供实际吞吐、原生依赖、Cordis 和迁移盘点结果后重估；每阶段结束根据完成证据更新余量。不为满足预定日期降低保存、同步和恢复门禁。若需尽早交付，优先减少首版协议和复杂插件范围，保留基础可用链路。

## 风险和处理

| 风险 | 处理与决策点 |
| --- | --- |
| Cordis API 未稳定 | 固定来源、自有 SDK、适配层与完整生命周期回归；P0 阻断项 |
| SQLite 原生 ABI/打包 | P0 在 Electron 与 Node、三平台验证；失败先解决驱动适配，不带病扩功能 |
| uni-app x 模式/原生模块 | 固定正式工具链，数据库和后台链路先于完整页面 |
| 协议语义不一致 | 驱动能力探测和故障测试；不合格驱动先备份/导入，双向同步走后端 |
| 旧功能隐含规则多 | 功能矩阵、黄金样本、保留未知字段和副本迁移 |
| 多端重复实现漂移 | Schema、样本、错误与版本统一，契约检查进入 CI |
| 包体/性能超标 | 逐包预算、按需连接器、懒加载与线程测量，不先加多个新运行时 |

任务落实到[实施清单](../整体重构实施清单.md)。勾选必须关联代码、测试或产物；本轮只完成设计文档，开发任务保持待实施。
